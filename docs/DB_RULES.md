# 백엔드 DB 개발 및 협업 규칙

**기술 스택:** Supabase (PostgreSQL)

**협업 환경:** GitHub / Codex / Claude Code

**DB 관리 방식:** 선언형 스키마 + Supabase CLI 마이그레이션

## 1. 기본 원칙

- DB 구조의 기준(SSOT)은 `supabase/schemas/`로 통일한다.
- 모든 DB 구조 변경은 Git에서 추적하고 마이그레이션으로 관리한다.
- 각 개발자는 독립된 브랜치와 로컬 DB에서 작업한다.
- 공유 개발 DB에는 검증 및 병합된 변경 사항만 반영한다.
- Codex와 Claude Code는 동일한 DB 작업 규칙을 따른다.

## 2. 스키마 및 마이그레이션 관리

**1. 선언형 스키마 관리**

DB 구조 변경은 `supabase/schemas/`의 도메인별 SQL 파일에서 수행한다.

테이블뿐 아니라 관련 인덱스, 제약조건, RLS 정책, 함수 등도 선언형 스키마로 관리한다.

**2. 마이그레이션 자동 생성**

마이그레이션은 원칙적으로 Supabase CLI로 생성하고, 생성된 SQL을 반드시 검토한다.

자동 생성이 지원되지 않는 다음 작업은 예외적으로 직접 작성할 수 있다.

- 데이터 입력 및 보정(INSERT, UPDATE, DELETE)
- Storage 버킷 생성 및 설정
- pg_cron 작업 등 자동 생성이 지원되지 않는 작업
- 그 외 CLI가 정상적으로 표현하지 못하는 변경

테스트용 초기 데이터는 가능하면 `seed.sql`로 관리한다.

**3. 직접 DB 변경 금지**

공유 개발 DB에서 Supabase Studio, SQL Editor 등을 이용해 스키마를 직접 수정하지 않는다.

모든 구조 변경은 스키마 파일 → 마이그레이션 → DB 반영 순서로 진행한다.

**4. 적용된 마이그레이션 수정 금지**

이미 공유 DB에 적용된 마이그레이션 파일은 수정하거나 삭제하지 않는다.

기존 변경을 되돌려야 한다면 새로운 마이그레이션을 생성한다.

**5. 파괴적 변경 사전 승인**

다음 변경은 작업 전 다른 백엔드 개발자와 협의한다.

- DROP TABLE / COLUMN
- RENAME TABLE / COLUMN
- 컬럼 타입 변경
- 데이터 삭제 또는 손실 가능성이 있는 작업
- 기존 API와 호환되지 않는 구조 변경

가능하면 기존 기능과의 호환성을 유지하면서 단계적으로 변경한다.

**6. 마이그레이션 충돌 처리**

다른 개발자의 마이그레이션이 먼저 develop에 병합되었다면 다음 원칙을 따른다.

- 최신 develop을 반영한다.
- 스키마 파일의 변경 사항을 병합한다.
- 내 마이그레이션이 공유 DB에 적용되지 않았는지 확인한다.
- 아직 공유되지 않은 마이그레이션만 삭제하고 최신 기준으로 재생성할 수 있다.
- 이미 적용된 마이그레이션은 보존하고 새로운 마이그레이션으로 처리한다.
- 재생성 이후 전체 마이그레이션을 검증한다.

마이그레이션 SQL을 무작정 합치거나 순서를 수동으로 변경하지 않는다.

## 3. 데이터베이스 보안

**7. RLS 적용 필수**

외부 API에 노출되는 애플리케이션 테이블에는 RLS를 반드시 활성화한다.

- SELECT / INSERT / UPDATE / DELETE별 권한을 검토한다.
- 사용자별 데이터 접근 범위를 명확하게 제한한다.
- 본인 데이터와 타인 데이터 접근을 구분한다.
- 기본적으로 최소 권한 원칙을 따른다.

내부 전용 테이블은 API 노출 여부와 접근 권한을 별도로 검토한다.

**8. SECURITY DEFINER 함수 관리**

`SECURITY DEFINER` 함수는 꼭 필요한 경우에만 사용한다.

- 원칙적으로 API에 노출되지 않는 `private` 스키마에 배치한다.
- `SET search_path = ''`를 설정한다.
- 함수 내부에서 테이블의 스키마를 명시한다.
- PUBLIC 및 불필요한 역할의 EXECUTE 권한을 회수한다.
- 필요한 역할에만 실행 권한을 명시적으로 부여한다.
- 함수 내부에서 사용자 인증 및 데이터 접근 권한을 검증한다.

**9. 관리자 키 관리**

Supabase Secret Key 및 `service_role` 키는 클라이언트에 포함하지 않는다.

- React Native 앱에 포함 금지
- Git 저장소에 커밋 금지
- 신뢰할 수 있는 백엔드 서버 또는 Edge Function에서만 사용
- 환경변수 또는 비밀 관리 시스템으로 보관
- 관리자 권한 사용 전 별도 인증 및 인가 수행

**10. DB 권한 및 접근 범위 검토**

새로운 테이블, View, Function을 추가할 때는 GRANT/REVOKE 권한을 함께 확인한다.

특히 RLS 우회 가능성이 있는 함수와 View는 별도로 검토한다.

## 4. Git 및 AI 개발 협업

**11. 기능별 브랜치 사용**

개발자별로 기능 브랜치를 생성하고, main에 직접 작업하지 않는다.

**12. 동일 테이블 동시 수정 허용**

서로 다른 기능에서 동일 테이블을 수정하는 것은 허용한다.

단, 다음 경우에는 작업 내용을 사전에 공유한다.

- 같은 컬럼이나 제약조건을 수정하는 경우
- 같은 RLS 정책 또는 DB 함수를 수정하는 경우
- 테이블 관계나 데이터 구조를 크게 변경하는 경우

작업자가 같은 테이블을 수정한다는 이유만으로 기능 개발을 분리하거나 제한하지 않는다.

**13. DB 변경 PR 상호 리뷰**

DB 구조가 변경되는 PR은 다른 백엔드 개발자의 리뷰를 받는다.

다음 사항을 확인한다.

- 변경 목적과 실제 SQL이 일치하는지
- 기존 기능에 영향을 주지 않는지
- RLS 및 권한 설정이 적절한지
- 데이터 손실 가능성이 있는지
- 불필요한 변경 사항이 포함되지 않았는지

**14. AI 작업 규칙 통일**

Codex와 Claude Code는 동일한 DB 관리 규칙을 따른다.

공통 규칙은 `docs/DB_RULES.md`에 작성한다.

- Codex: `AGENTS.md`에서 공통 문서 참조
- Claude Code: `CLAUDE.md`에서 공통 문서 참조

두 AI가 독립적으로 DB 구조를 수정하더라도 동일한 기준을 적용하도록 한다.

**15. 공유 DB 배포 경로 통일**

공유 개발 DB는 승인된 PR을 develop에 병합한 뒤 GitHub Actions로 자동 배포한다. 배포 기준 브랜치는 develop이며, main 병합으로 공유 개발 DB를 배포하지 않는다.

- 워크플로: `.github/workflows/deploy-shared-db.yml`
- develop의 push 이벤트에서 관련 DB 파일 또는 워크플로가 변경됐을 때 실행한다. 실행 커밋이 develop에 병합된 PR의 병합 커밋과 일치하고 승인 상태가 `APPROVED`여야 배포한다. 직접 push는 배포 전에 차단한다.
- 로컬 임시 DB에서 전체 마이그레이션·pgTAP·lint·Advisors 검증에 성공한 정확한 커밋만 배포한다.
- GitHub Environment `shared-development`에 대상 프로젝트와 접속 정보를 보관하고 develop에서만 사용한다.
- 원격 DB 연결은 명시적인 IPv4 Session pooler(5432, TLS)를 사용한다. 원격 이력 조회와 `db push --dry-run` 성공 후에만 실제 적용한다.
- 배포는 한 번에 하나씩 실행하며 실행 중인 배포를 취소하지 않는다. 각 실행의 정확한 push 커밋을 검증·배포하며 대기 중 실행이 통합돼도 해당 커밋에 포함된 미적용 마이그레이션을 함께 반영한다.
- 원격 적용은 대기 중인 마이그레이션의 `db push --dry-run` 확인 후 `db push`만 실행한다. 원격 reset·자동 repair·seed·Vault 설정 변경은 수행하지 않는다.
- 실패하면 GitHub Actions에서 원인을 확인하고 해결 후 같은 실행을 다시 실행한다. 승인되지 않은 PR을 관리자 권한으로 먼저 병합한 경우 승인된 후속 PR로 정상 배포 경로를 복구한다.

초기 접속 정보 등록·최초 배포 전 기존 DB의 마이그레이션 이력 확인·장애 대응은 `docs/DB_DEPLOYMENT.md`를 따른다. 운영 DB 자동 배포는 이번 설정에 포함하지 않는다.

개별 기능 브랜치에서 공유 DB에 직접 `db push`하지 않는다.

## 5. PR 제출 전 필수 검증

DB 변경이 있는 PR은 아래 항목을 확인한다.

- [ ] 최신 develop 변경 사항을 반영했다.
- [ ] 스키마 파일과 마이그레이션 파일을 함께 수정했다.
- [ ] 자동 생성된 마이그레이션 SQL을 검토했다.
- [ ] `supabase db reset`이 정상 완료되었다.
- [ ] `supabase test db` 테스트가 통과했다.
- [ ] `supabase db lint --fail-on error`가 통과했다.
- [ ] Security / Performance Advisors 경고를 검토했다.
- [ ] 심각한 보안 문제를 해결하고, 의도된 예외는 PR에 기록했다.
- [ ] 변경된 DB 구조를 기준으로 TypeScript 타입을 재생성했다.
- [ ] 생성된 타입 파일을 함께 커밋했다.
- [ ] 데이터 손실 및 기존 기능 영향 여부를 검토했다.

RLS 또는 접근 권한을 변경한 경우에는 정상 접근뿐 아니라 **권한이 없는 사용자의 접근 차단도 테스트**한다.

※ pgTAP 테스트는 `supabase/tests/`에 실제 테스트 케이스를 작성해 관리한다. 테스트가 없는 상태에서 명령이 실행된 것만으로 검증 완료로 간주하지 않는다.

## 6. 표준 작업 순서

1. 최신 develop을 반영하고 기능 브랜치를 생성한다.
2. Codex 또는 Claude Code로 기능을 개발한다.
3. DB 변경이 필요하면 `supabase/schemas/`를 수정한다.
4. Supabase CLI로 마이그레이션을 생성한다.
5. 생성된 SQL을 검토한다.
6. 로컬 DB에서 전체 마이그레이션을 검증한다.
7. DB 테스트 및 보안 검사를 실행한다.
8. TypeScript 타입을 재생성한다.
9. PR을 생성하고 상대 개발자의 리뷰를 받는다.
10. 승인 후 develop에 병합하고 GitHub Actions의 공유 개발 DB 검증·배포 결과를 확인한다.

## 7. 주요 CLI 명령

**마이그레이션 생성 (pg-delta 기준)**

`supabase db schema declarative sync -f <migration_name> --no-apply`

**로컬 DB 전체 마이그레이션 검증**

`supabase db reset`

**DB 테스트 실행**

`supabase test db`

**DB 오류 검사**

`supabase db lint --fail-on error`

**DB Advisors 검사**

`supabase db advisors`

**TypeScript 타입 생성**

`supabase gen types --lang typescript --local > database.types.ts`

타입 출력 경로는 프로젝트에서 사용하는 실제 경로로 통일한다.

**공유 개발 DB 반영 전 확인**

`supabase db push --dry-run`

**공유 개발 DB 반영 (지정된 배포 경로에서만)**

`supabase db push`

### CLI 사용 주의사항

- 프로젝트의 `config.toml`에서 pg-delta 사용 여부를 확인한다.
- 위 선언형 마이그레이션 생성 명령은 pg-delta 활성화를 전제로 한다.
- `db reset`은 로컬 데이터를 초기화하므로 필요한 데이터는 미리 보관한다.
- `db reset --linked` 등 원격 DB 초기화 명령은 일반 작업에서 사용하지 않는다.
- Advisors 경고는 무조건 0개를 요구하기보다 보안 위험과 의도된 설정을 구분해 처리한다.

## 최종 원칙

**스키마는 하나의 기준으로 관리하고, 마이그레이션은 이력으로 보존한다.**

Codex와 Claude Code가 동일 테이블을 동시에 수정하는 것은 허용하되, Git 병합과 마이그레이션 검증을 통해 충돌을 해결한다.

**공유 DB는 직접 수정하지 않으며, 모든 변경은 검증된 마이그레이션으로 반영한다.**
